Overview

Satellite altimeters don't sample the Greenland Ice Sheet evenly. Their orbits converge towards the north, so high-latitude regions such as the Northeast Greenland Ice Stream (NEGIS) are crossed far more often than southern outlet glaciers such as Helheim. That matters for my PhD: the more points a region gets, the more reliably we can measure how fast its surface is rising or falling (dh/dt).

To show this fairly, I needed two things: a way to compare data density between regions without the grid itself biasing the answer, and a way to fit dh/dt in every grid cell across the ice sheet quickly enough to iterate on the method. This project does both, by combining a new equal-area discrete global grid, A5, with DuckDB, the query engine behind my altimetry archive work.

The result: per-cell elevation-change fits over ~94 million points per mission, run as a handful of SQL passes, with no Python loop over cells and no data loaded into memory up front.

Data coverage

Data

  • Satellite altimetry: CryoSat-2 (CryoTEMPO, Baseline D) and ICESat-2 point elevations over Greenland, roughly 94 million points per mission, stored in a DuckDB database and queried in place.
  • Study sites: NEGIS, Upernavik Isstrøm (UI), Russell Glacier and Helheim Glacier, spanning roughly 66–80°N.
  • Grid: A5 cells at resolutions 9–12 (130 km² down to 2 km²). EPSG:3413 (NSIDC Polar Stereographic North) is used only to draw the maps.

Methods

1. Why the grid matters

To compare data density between regions, you count points per cell and divide by the cell's area. That only works if the cells really are the area you think they are. A square grid on a polar map isn't: map projections stretch the ground, so equal squares on the map cover different amounts of ice. Popular global grids such as H3 have the same problem in a different form. A5 is built so that every cell at a given resolution covers exactly the same area, anywhere on Earth.

Being a discrete global grid system (DGGS) brings three more benefits that turned out to matter as much as equal area:

  • Cells are integers. Every point gets a 64-bit cell ID, so grouping, filtering and joining datasets become fast integer operations rather than geometry tests.
  • Cells nest. Above the coarsest level, each A5 cell contains exactly four children at the next resolution. Counts computed once at a fine resolution can be added up to any coarser resolution, with no second pass over the raw data.
  • No projection to choose. Cells are defined on the globe, so the same pipeline works unchanged for Antarctica or anywhere else.

2. Data density: counting points per cell

The first output is a map of how many measurements each part of the ice sheet receives, in points per km² per year. DuckDB scans the database once, assigns every point to an A5 cell with the a5 community extension, and counts per cell. Coarser maps come from rolling those counts up to parent cells.

3. The DuckDB trick: fitting from summary statistics

Fitting dh/dt means running a small regression in every cell: hundreds of thousands of them. The usual approach loops over cells in Python, pulling out each cell's points and fitting them one at a time. That's simple, but the loop overhead dominates.

The key observation is that an ordinary least-squares fit doesn't need the points themselves, only each cell's means and covariances. DuckDB can compute those for every cell in a single GROUP BY, streaming through the data in parallel. The tiny per-cell systems of equations are then solved all at once in NumPy.

The loop costs grow with the number of cells; the SQL approach costs a few scans of the data however many cells there are. 

-- one fit for every cell: means + covariances, nothing else
SELECT cell, count(*) AS n, avg(h) AS m_h, avg(t) AS m_t,
       covar_pop(dx, dx) AS c_xx, covar_pop(dx, t) AS c_xt, covar_pop(t, t) AS c_tt,
       covar_pop(h, dx)  AS c_hx, covar_pop(h, t)  AS c_ht   -- ...one per pair of terms
FROM points WHERE keep
GROUP BY cell
HAVING count(*) >= 40 AND max(t) - min(t) >= 2;

4. The model

In each cell I fit the model-fit approach used for CryoSat-2 elevation change at the Centre for Polar Observation and Modelling (McMillan et al., 2016; Slater et al., 2021). A quadratic surface absorbs the topography within the cell, a heading term absorbs differences between ascending and descending passes, and the time term gives the rate of change:

h = h0 + a1x + a2y + a3x2 + a4y2 + a5xy + a6·heading + (dh/dt)·t

For CryoSat-2, changes in radar backscatter can masquerade as elevation change, so the fitted rate is corrected afterwards using the relationship between elevation and backscatter power in each cell. Outliers are handled by iterative 3σ rejection: fit, drop points far from the fit, refit. Cells are kept only if they pass the published quality checks (at least 40 points over at least 2 years, residual RMS ≤ 12 m, |dh/dt| ≤ 10 m/yr, surface slope ≤ 5°). A simpler plane-only model is kept alongside for comparison.

Some details aren't fully specified in the papers, so they are my interpretation: the backscatter correction uses time-detrended residuals over the whole record rather than a moving window, and "heading" is the ascending/descending flag.

5. Testing against a known answer

Before trusting it on real data, I built a synthetic ice sheet where the true dh/dt is known: a sloping, undulating surface, measurement noise, 3% gross outliers, a 0.4 m offset between ascending and descending passes, and a backscatter signal that leaks into elevation. Then I checked whether each model recovers the truth.

What I learned

  • Reframe the computation, not just the code. Recognising that a regression only needs summary statistics turned hundreds of thousands of small fits into a few database scans.
  • The grid is part of the method. Choosing a grid looks like a plotting decision, but it decides whether a comparison between regions is fair. Equal-area cells remove a bias I would otherwise have had to correct for.
  • Hierarchies pay off twice. Nested cells made coarse summaries free in the analysis, and they are exactly what an interactive map needs to switch detail as you zoom.
  • Validate on a known answer. A synthetic test with planted biases showed which model terms actually matter, before any real data was involved.
  • New tools come with rough edges. A5 is young: its DuckDB extension needs installing per machine, and its cell IDs have changed between versions. Pinning versions and checking a known point at start-up kept the pipeline honest.

Next steps: run both missions across the full record, publish the interactive map, and compare against independent airborne laser altimetry.
